# Requirements Analyst

[![CI](https://github.com/targetfff/requirements-analyst/actions/workflows/ci.yml/badge.svg)](https://github.com/targetfff/requirements-analyst/actions/workflows/ci.yml)

Одностраничное веб-приложение для анализа требований к программным продуктам с помощью Google Gemini. Пользователь описывает идею проекта, получает структурированный бизнес-анализ, уточняет и изменяет требования, затем переходит к системному анализу.

Приложение построено вокруг одного тематического чата. История сообщений и версии требований сохраняются в PostgreSQL, а для работы с ними используется асинхронный FastAPI backend. Доступ к чату открывается после ввода ключа, заданного на сервере.

## Стек

- Google Gemini API
- LangChain Core / langchain-google-genai
- SQLAlchemy 2.x Async / asyncpg
- PostgreSQL 18

- HTML / CSS / JavaScript без frontend-фреймворков

- Ruff
- Docker / Docker Compose
- GitHub Actions

## Возможности

- вход по общему ключу доступа с проверкой на клиенте и сервере;
- валидация ключа: от 8 до 255 символов, латинские буквы, цифры, дефис и подчёркивание;
- сессия с подписанной `HttpOnly` cookie без хранения ключа доступа в браузере;
- один чат с сообщениями пользователя и ассистента, датой и временем;
- сохранение переписки и требований при обновлении страницы и перезапуске приложения;
- **Business Analyst** — оценка реализуемости, риски, вопросы, функциональные требования, критерии приёмки и MVP;
- **System Analyst** — архитектура, технологии, модели данных, API и взаимодействие компонентов;
- **Уточнение** — обычный диалог с Gemini или явное изменение текущих требований;
- нумерация функциональных требований (`FR-01`, `FR-02`, ...) и сохранение их версий;
- отметка системного анализа, который устарел после изменения требований;
- ограниченный контекст последних сообщений с передачей актуальных требований модели;
- валидация сообщений от 1 до 500 символов, запрет пустых сообщений;
- блокировка повторной отправки во время ожидания ответа и отображение ошибок API;
- светлая и тёмная темы, адаптивный интерфейс, очистка истории;
- защита от конкурентного изменения переписки через ревизию диалога;
- Alembic-миграции, автоматизированные тесты, Ruff и GitHub Actions CI.

## Архитектура

```text
Browser: HTML / CSS / JavaScript
       |
       | HTTP, port 8000
       v
Nginx (frontend + reverse proxy)
       |
       +--> Static files (HTML / CSS / JS)
       |
       +--> /api/*
                |
                v
           FastAPI
                |
                +--> Auth: ACCESS_KEY -> signed HttpOnly session
                |
                +--> Chat API
                        |
                        v
                  Chat Service
                        |
                        +--> ConversationRepository
                        |         |
                        |         v
                        |     PostgreSQL
                        |     - conversation
                        |     - messages
                        |     - requirements_versions
                        |
                        +--> Analyst Service
                                  |
                                  v
                         LangChain / Gemini API
```

Обработка сообщения состоит из трёх этапов:

1. Backend читает ревизию диалога, историю и актуальную версию требований из PostgreSQL.
2. Сервис вызывает Gemini **без открытой транзакции БД**. Для структурированного анализа ответ проверяется Pydantic-схемой.
3. Backend проверяет, что ревизия не изменилась, и в одной транзакции сохраняет сообщения и, при необходимости, новую версию требований.

Так разделены HTTP-обработчики, бизнес-логика, работа с LLM и операции с базой данных.

## Запуск

Для запуска нужны **Git**, **Docker с Docker Compose** и действующий ключ [Google Gemini API](https://aistudio.google.com/apikey).

**1. Клонировать репозиторий:**

```bash
git clone https://github.com/targetfff/requirements-analyst.git
cd requirements-analyst
```

**2. Создать локальный `.env` из готового примера:**

```bash
cp .env.example .env
```

В полученном `.env` **вставьте свой `GOOGLE_API_KEY`**. Остальные переменные уже содержат демонстрационные значения для локального запуска.

**3. Собрать и запустить приложение:**

```bash
docker compose up --build -d
```

Backend автоматически выполняет `alembic upgrade head` перед запуском Uvicorn, поэтому отдельная команда для миграций не нужна.

**4. Проверить состояние контейнеров:**

```bash
docker compose ps
```

Приложение доступно по адресу **http://localhost:8000**. На экране входа используйте значение `ACCESS_KEY` из `.env`. Проверка состояния API — **http://localhost:8000/api/health**.

## Переменные окружения

Все параметры описаны в `.env.example`. После копирования в `.env` для локального запуска требуется заполнить только `GOOGLE_API_KEY`.

| Переменная | Назначение |
| --- | --- |
| `GOOGLE_API_KEY` | Личный ключ Gemini API. **Единственная переменная, которую нужно заполнить перед локальным запуском**. |
| `POSTGRES_PASSWORD` | Пароль пользователя PostgreSQL. В примере указан публичный демонстрационный пароль; он должен содержать URL-безопасные символы, поскольку входит в `DATABASE_URL`. |
| `ACCESS_KEY` | Общий ключ для входа в чат (8–255 символов: латинские буквы, цифры, `-` и `_`). В примере задан демонстрационный ключ. |
| `SESSION_SECRET` | Отдельный секрет для HMAC-подписи сессионной cookie, не менее 32 байт. Значение в примере предназначено только для локальной демонстрации. |
| `GEMINI_MODEL` | Модель Gemini, используемая backend. |
| `APP_ENV` | `development` для локального запуска; `production` для развёртывания. |
| `SESSION_COOKIE_SECURE` | Дополнительное включение флага `Secure` для cookie при HTTPS. В production он включается автоматически. |
| `APP_ORIGIN` | Необязательный внешний origin приложения, например `https://example.com`, если HTTPS завершается на обратном прокси. |

`DATABASE_URL` в Docker Compose собирается автоматически из `POSTGRES_PASSWORD` и адреса контейнера `db`. При запуске backend вне Docker по умолчанию используется локальная SQLite через `aiosqlite`.

**Безопасность:** `.env.example` содержит заведомо публичные значения только для локальной разработки. Они **не являются защищёнными секретами**. Перед размещением приложения на сервере замените `POSTGRES_PASSWORD`, `ACCESS_KEY` и `SESSION_SECRET`, настройте HTTPS, `APP_ENV=production` и при необходимости `APP_ORIGIN`. Если PostgreSQL уже была инициализирована, смените пароль также у существующего пользователя БД: изменение `.env` само по себе его не обновляет. Файл `.env` исключён из Git и не должен коммититься.

## API

Снаружи открыт только Nginx на `127.0.0.1:8000`, который передаёт `/api/*` в FastAPI. Все endpoints чата требуют авторизованную сессию.

### Авторизация

```http
POST /api/auth/login
Content-Type: application/json
Origin: http://localhost:8000
```

```json
{
  "key": "<ACCESS_KEY из .env>"
}
```

При успешной проверке сервер отвечает `200 OK` и устанавливает подписанную cookie. Далее браузер отправляет её автоматически.

```text
GET  /api/auth/me       Проверить сессию
POST /api/auth/logout   Выйти и удалить cookie в браузере
```

Для изменяющих запросов, включая вход и выход, сервер проверяет заголовок `Origin`. При работе через браузер на том же адресе он передаётся автоматически.

### Отправка сообщения

```http
POST /api/messages
Content-Type: application/json
```

Бизнес-анализ:

```json
{
  "mode": "business_analyst",
  "text": "Нужен сервис согласования документов между сотрудниками и руководителями"
}
```

Уточнение без изменения документа требований:

```json
{
  "mode": "clarification",
  "text": "Какие роли нужны в этой системе?"
}
```

Уточнение с запросом на изменение требований:

```json
{
  "mode": "clarification",
  "text": "Добавь уведомления о согласовании документа",
  "update_requirements": true
}
```

Системный анализ по актуальным бизнес-требованиям:

```json
{
  "mode": "system_analyst"
}
```

Последний запрос допускается только после формирования бизнес-требований. Ответ `201 Created` содержит сообщения пользователя и ассистента, актуальные требования и признак необходимости дополнительного уточнения:

```text
user
assistant
requirements
requires_edit_clarification
```

### История и очистка

```text
GET    /api/chat       История сообщений и актуальные требования
GET    /api/messages   Список сообщений
DELETE /api/messages   Очистить переписку и версии требований
GET    /api/health     Проверка доступности API без авторизации
```

Основные коды ошибок:

| Код | Значение |
| --- | --- |
| `401` | Неверный ключ или отсутствующая/истёкшая сессия |
| `403` | Недопустимый `Origin` |
| `409` | Требования ещё не сформированы или диалог изменён конкурентным запросом |
| `422` | Некорректный формат ключа или сообщения |
| `502` | Ошибка анализа или некорректный ответ Gemini |
| `503` | Gemini или авторизация не настроены на сервере |

## Конкурентные запросы

Для одного диалога хранится поле `conversation.revision`.

Перед обращением к Gemini backend считывает текущую ревизию. После получения ответа выполняется условное обновление ревизии (compare-and-swap). Если другая операция успела изменить или очистить чат, запрос возвращает `409 Conflict` и **не сохраняет устаревший ответ**.

Сообщения и новая версия требований сохраняются в одной транзакции. При ошибке записи транзакция откатывается.

## Версионирование требований

Актуальный документ хранится в `requirements_versions` и включает:

- функциональные требования с постоянными идентификаторами `FR-*`;
- критерии приёмки;
- состав MVP;
- номер версии и следующий доступный номер требования.

Первый успешный бизнес-анализ с непустым списком требований создаёт версию `1`. В режиме уточнения пользователь может явно включить изменение требований. Gemini возвращает структурированное решение о добавлении, замене или удалении элементов; backend проверяет изменения перед сохранением новой версии.

Удалённые номера `FR-*` повторно не используются. Системный анализ связан с версией требований, на основе которой он был подготовлен. Если требования изменились, такой анализ помечается как устаревший.

## Режимы анализа

**Business Analyst** формирует оценку реализуемости, разделяет факты и допущения, выделяет риски, функциональные требования, критерии приёмки, MVP и вопросы для заказчика.

**System Analyst** использует актуальные бизнес-требования для подготовки архитектуры, списка технологий, моделей данных, API и схемы взаимодействия компонентов в текстовом виде.

**Уточнение** поддерживает свободный диалог. Если включён переключатель «Изменить актуальные требования», модель вместо обычного ответа возвращает структурированные изменения документа.

В структурированных режимах ответы Gemini проверяются Pydantic-схемами. Генерируемые материалы являются предложениями для обсуждения и требуют проверки человеком.

## Контекст Gemini

Для очередного запроса backend использует последние **24 сообщения** (до 12 полных пар «пользователь — ассистент») с ограничением общего объёма контекста в **16 000 символов**. Длинные ответы из старой истории сокращаются.

Актуальный документ требований передаётся отдельно от сокращённой истории. Поэтому важные текущие требования не теряются только из-за увеличения длины переписки.

Вызов Gemini асинхронный и выполняется вне транзакции PostgreSQL. Для LLM заданы таймауты и ограниченное число повторных попыток; ошибки передаются клиенту в безопасном виде.

## Авторизация и безопасность

Ключ `ACCESS_KEY` хранится в переменных окружения backend и передаётся только при входе в JSON-теле `POST /api/auth/login`. Сверка выполняется через `hmac.compare_digest`.

После входа браузер получает подписанную `HttpOnly` cookie со временем жизни **24 часа**, `SameSite=Lax` и `Secure` в production-режиме. Подпись создаётся с использованием отдельного `SESSION_SECRET`. Изменяющие запросы проверяются по `Origin`, а ответы авторизации не кэшируются.

Для отображения текста Gemini frontend использует `marked` и очищает HTML через `DOMPurify`; структурированные результаты собираются через безопасные DOM-операции.

**Ограничение текущего решения:** ключ общий, а чат один на всё приложение. Это не система индивидуальных аккаунтов и не изолированное рабочее пространство для нескольких пользователей. Для публичного размещения используйте HTTPS, настройте `APP_ENV=production` и `APP_ORIGIN`, а также отдельные секреты.

## Тесты

Тесты покрывают:

- вход, выход, истечение срока сессии, повреждённые cookie и проверку `Origin`;
- правила валидации ключа и сообщений;
- API-контракты, сохранение и очистку истории;
- бизнес-анализ, системный анализ и контекстное уточнение;
- изменение требований, сохранение идентификаторов и актуальность аналитики;
- ошибки Gemini и отсутствие частично сохранённых результатов;
- конкурентные запросы, очистку истории во время ответа модели и rollback;
- миграции Alembic и совместимость старой истории.

В GitHub Actions для текущей версии проекта успешно выполнено **53 тестовых сценария**. Реальный Gemini API в тестах не вызывается: внешние ответы подменяются моками, а БД создаётся во временной SQLite.

Локальный запуск из каталога `backend/` после установки Python 3.14:

```bash
cd backend
python -m pip install -r requirements-dev.txt
python -m pytest -v
```

В production Docker-образ тесты и dev-зависимости не входят, поэтому они запускаются локально или в CI, а не через `docker compose exec backend pytest`.

## Локальная разработка

При запуске backend без Docker переменная `DATABASE_URL` по умолчанию указывает на локальную SQLite через `aiosqlite`. Для PostgreSQL необходимо задать собственный `DATABASE_URL`. В обоих случаях перед первым запуском примените миграции:

```bash
cd backend
python -m pip install -r requirements-dev.txt
python -m alembic upgrade head
python -m uvicorn app.main:app --reload
```

При таком запуске API доступен по адресу `http://127.0.0.1:8000`, но frontend с Nginx не запускается. Для проверки всего приложения используйте Docker Compose.

## Остановка

Остановить контейнеры, сохранив историю в PostgreSQL volume:

```bash
docker compose down
```

Остановить контейнеры **и безвозвратно удалить локальные данные PostgreSQL**:

```bash
docker compose down -v
```

После удаления volume при следующем `docker compose up --build -d` база будет создана заново, а миграции применятся автоматически.

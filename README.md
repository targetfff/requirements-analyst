# Requirements Analyst

[![CI](https://github.com/targetfff/requirements-analyst/actions/workflows/ci.yml/badge.svg)](https://github.com/targetfff/requirements-analyst/actions/workflows/ci.yml)

Одностраничное веб-приложение для анализа требований к программным продуктам с помощью Google Gemini. Пользователь описывает идею проекта, получает структурированный бизнес-анализ, уточняет и изменяет требования, затем переходит к системному анализу.

Приложение построено вокруг одного тематического чата. История сообщений и версии требований сохраняются в PostgreSQL, а для работы с ними используется асинхронный FastAPI backend. Доступ к чату открывается после ввода ключа, заданного на сервере.

## Запуск

Для запуска нужны **Git Bash**, **Docker с Docker Compose** и действующий ключ [Google Gemini API](https://aistudio.google.com/apikey).

**1. Клонировать репозиторий:**

```bash
git clone https://github.com/targetfff/requirements-analyst.git
cd requirements-analyst
```

**2. Создать локальный `.env` из готового примера:**

```bash
cp .env.example .env
```

В полученном `.env` **вставьте свой `GOOGLE_API_KEY`**. Остальные переменные уже содержат демонстрационные значения для локального запуска.

**3. Собрать и запустить приложение:**

```bash
docker compose up --build -d
```

Backend автоматически выполняет `alembic upgrade head` перед запуском Uvicorn, поэтому отдельная команда для миграций не нужна.

**4. Проверить состояние контейнеров:**

```bash
docker compose ps
```

Приложение доступно по адресу **http://localhost:8000**. На экране входа используйте значение `ACCESS_KEY` из `.env`. Проверка состояния API — **http://localhost:8000/api/health**.

## Сценарии для ручной проверки (необязательно)

Ниже приведены два сценария для знакомства с приложением. Начальные идеи доступны в интерфейсе в виде **готовых примеров (Starter Prompts)** — достаточно выбрать нужный вариант.

Каждый сценарий включает пять этапов: **бизнес-анализ → системный анализ → изменение требований → повторный бизнес-анализ → повторный системный анализ**.

### Сценарий 1. Бронирование переговорных

1. **Business Analyst.** Выбрать готовый пример бронирования переговорных.
2. **System Analyst.** Нажать **«Перейти к системному анализу»**.
3. **Изменение требований.** Выбрать режим **«Уточнение»**, включить **«Изменить актуальные требования»** и отправить:

   > Добавь обязательный перерыв 15 минут между бронированиями одной комнаты. Остальные требования сохрани.

4. **Повторный бизнес-анализ.** Нажать **«Повторить бизнес-анализ»**.
5. **Повторный системный анализ.** Нажать **«Повторить системный анализ»**.

### Сценарий 2. Интернет-магазин

Перед началом очистить историю предыдущего сценария кнопкой **«Очистить»**.

1. **Business Analyst.** Выбрать готовый пример интернет-магазина.
2. **System Analyst.** Нажать **«Перейти к системному анализу»**.
3. **Изменение требований.** Выбрать режим **«Уточнение»**, включить **«Изменить актуальные требования»** и отправить:

   > Добавь отмену неоплаченного заказа в течение 30 минут. После оплаты отмена недоступна. Остальные требования не меняй.

4. **Повторный бизнес-анализ.** Нажать **«Повторить бизнес-анализ»**.
5. **Повторный системный анализ.** Нажать **«Повторить системный анализ»**.

В обоих сценариях можно проверить версионирование требований, отметку устаревшего системного анализа, повторную генерацию анализов с учётом изменений и сохранение истории после перезагрузки страницы.

## Возможности

- Авторизация по ключу доступа с валидацией и защищённой сессией через `HttpOnly` cookie.
- Тематический чат с Gemini, сохранением истории и контекста диалога.
- Три режима работы с LLM на основе специализированных системных промптов:
   - **Business Analyst** — анализ требований, рисков, критериев приёмки и MVP.
   - **System Analyst** — проектирование архитектуры, моделей данных, API и взаимодействий компонентов.
   - **Уточнение** — обсуждение идеи и внесение изменений в существующие требования.
- Версионирование требований и повторный анализ после их изменения.
- Валидация сообщений, обработка ошибок и защита от конкурентных запросов.
- Адаптивный интерфейс со светлой и тёмной темами.
- PostgreSQL для хранения данных, Alembic-миграции, тесты и CI.

## Стек

- **Backend:** Python 3.15.2, FastAPI / Uvicorn, Pydantic v2 / pydantic-settings.
- **LLM:** Google Gemini API, LangChain Core / langchain-google-genai.
- **База данных:** PostgreSQL 18, SQLAlchemy 2.x Async / asyncpg, Alembic.
- **Frontend:** HTML / CSS / JavaScript без фреймворков, Nginx, marked / DOMPurify.
- **Тестирование:** pytest, httpx, aiosqlite, Ruff.
- **Инфраструктура:** Docker / Docker Compose, GitHub Actions.

## Архитектура

```text
Browser: HTML / CSS / JavaScript
       |
       | HTTP, port 8000
       v
Nginx (frontend + reverse proxy)
       |
       +--> Static files (HTML / CSS / JS)
       |
       +--> /api/*
                |
                v
           FastAPI
                |
                +--> Auth: ACCESS_KEY -> signed HttpOnly session
                |
                +--> Chat API
                        |
                        v
                  Chat Service
                        |
                        +--> ConversationRepository
                        |         |
                        |         v
                        |     PostgreSQL
                        |     - conversation
                        |     - messages
                        |     - requirements_versions
                        |
                        +--> Analyst Service
                                  |
                                  v
                         LangChain / Gemini API
```

Обработка сообщения состоит из трёх этапов:

1. Backend читает ревизию диалога, историю и актуальную версию требований из PostgreSQL.
2. Сервис вызывает Gemini **без открытой транзакции БД**. Для структурированного анализа ответ проверяется Pydantic-схемой.
3. Backend проверяет, что ревизия не изменилась, и в одной транзакции сохраняет сообщения и, при необходимости, новую версию требований.

Так разделены HTTP-обработчики, бизнес-логика, работа с LLM и операции с базой данных. В контекст Gemini включаются последние 24 сообщения (до 12 пар, не более 16 000 символов); актуальные требования передаются отдельно.

## API

Снаружи открыт только Nginx на `127.0.0.1:8000`, который передаёт `/api/*` в FastAPI. Все endpoints чата требуют авторизованную сессию.

### Авторизация

```http
POST /api/auth/login
Content-Type: application/json
Origin: http://localhost:8000
```

```json
{
  "key": "<ACCESS_KEY из .env>"
}
```

При успешной проверке сервер отвечает `200 OK` и устанавливает подписанную cookie. Далее браузер отправляет её автоматически.

```text
GET  /api/auth/me       Проверить сессию
POST /api/auth/logout   Выйти и удалить cookie в браузере
```

Для изменяющих запросов, включая вход и выход, сервер проверяет заголовок `Origin`. При работе через браузер на том же адресе он передаётся автоматически.

### Отправка сообщения

`POST /api/messages`

Пример JSON со всеми параметрами:

```json
{
  "mode": "clarification",
  "text": "Добавь уведомления о согласовании документа",
  "update_requirements": true
}
```

**Параметры:**

- `mode` — режим работы: `business_analyst`, `system_analyst` или `clarification`.
- `text` — текст сообщения (1–500 символов). Необязателен для `system_analyst`.
- `update_requirements` — изменение текущих требований (`true` / `false`). Используется только в режиме `clarification`, по умолчанию `false`.

При успешной обработке API возвращает `201 Created` с сообщениями пользователя и ассистента, актуальными требованиями и результатом анализа.

### История и очистка

```text
GET    /api/chat       История сообщений и актуальные требования
GET    /api/messages   Список сообщений
DELETE /api/messages   Очистить переписку и версии требований
GET    /api/health     Проверка доступности API без авторизации
```

Основные коды ошибок:

| Код | Значение |
| --- | --- |
| `401` | Неверный ключ или отсутствующая/истёкшая сессия |
| `403` | Недопустимый `Origin` |
| `409` | Требования ещё не сформированы или диалог изменён конкурентным запросом |
| `422` | Некорректный формат ключа или сообщения |
| `502` | Ошибка анализа или некорректный ответ Gemini |
| `503` | Gemini или авторизация не настроены на сервере |

## Версионирование требований

Актуальный документ хранится в `requirements_versions` и включает:

- функциональные требования с постоянными идентификаторами `FR-*`;
- критерии приёмки;
- состав MVP;
- номер версии и следующий доступный номер требования.

Первый успешный бизнес-анализ с непустым списком требований создаёт версию `1`. В режиме уточнения пользователь может явно включить изменение требований. Gemini возвращает структурированное решение о добавлении, замене или удалении элементов; backend проверяет изменения перед сохранением новой версии.

Удалённые номера `FR-*` повторно не используются. Системный анализ связан с версией требований, на основе которой он был подготовлен. Если требования изменились, такой анализ помечается как устаревший.

## Авторизация и безопасность

Ключ `ACCESS_KEY` хранится в переменных окружения backend и передаётся только при входе в JSON-теле `POST /api/auth/login`. Сверка выполняется через `hmac.compare_digest`.

После входа браузер получает подписанную `HttpOnly` cookie со временем жизни **24 часа**, `SameSite=Lax` и `Secure` в production-режиме. Подпись создаётся с использованием отдельного `SESSION_SECRET`. Изменяющие запросы проверяются по `Origin`, а ответы авторизации не кэшируются.

Для отображения текста Gemini frontend использует `marked` и очищает HTML через `DOMPurify`; структурированные результаты собираются через безопасные DOM-операции.

**Ограничение текущего решения:** ключ общий, а чат один на всё приложение. Это не система индивидуальных аккаунтов и не изолированное рабочее пространство для нескольких пользователей. Для публичного размещения используйте HTTPS, настройте `APP_ENV=production` и `APP_ORIGIN`, а также отдельные секреты.

## Переменные окружения

Все параметры описаны в `.env.example`. Для локального запуска достаточно скопировать файл в `.env` и заполнить только `GOOGLE_API_KEY`. Остальные переменные уже имеют значения по умолчанию.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `GOOGLE_API_KEY` | Не задано | Ключ доступа к Google Gemini API. **Необходимо заполнить вручную.** |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite` | Используемая модель Gemini. |
| `POSTGRES_PASSWORD` | `example-local-postgres` | Пароль пользователя PostgreSQL. |
| `ACCESS_KEY` | `example-local-access` | Ключ авторизации в приложении. |
| `SESSION_SECRET` | `example-local-session-secret-not-for-production` | Секрет для подписи сессионных cookie. |
| `APP_ENV` | `development` | Режим работы приложения. |
| `SESSION_COOKIE_SECURE` | `false` | Использование Secure cookie при HTTPS. |
| `APP_ORIGIN` | Не задано | Внешний адрес приложения при использовании обратного прокси. |

`DATABASE_URL` автоматически формируется в Docker Compose на основе настроек PostgreSQL.

## Тесты и качество кода

В текущем наборе **27 тестовых сценариев**, которые запускаются в GitHub Actions. pytest проверяет авторизацию, валидацию запросов, работу режимов анализа, контекст, сохранение истории, изменение требований и обработку ошибок Gemini. Внешние вызовы LLM подменяются моками, а для тестов используется SQLite.

Запуск из каталога `backend/` после установки Python 3.15.2 и зависимостей из `requirements-dev.txt`:

```bash
python -m pytest -v
python -m ruff check .
```

Конфигурация Ruff находится в `backend/pyproject.toml`.

